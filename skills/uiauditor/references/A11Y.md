# A11Y: Accessibility and Inclusive Markup

Weight 22. Always active. Floor dimension: one A11Y Critical that is not Suspected caps the overall score at 69.
Owns: whether the UI as written works with a keyboard and assistive technology: accessible names, form labels, keyboard paths, focus management and visibility, zoom, text alternatives and captions, ARIA roles and states, announcements, and color independence. It covers React Native accessibility props too.
Not here: the wrong element when the control still works (SEM-R1); headings, landmarks, and `<html lang>` (SEM-R2, SEM-R4); a `<dialog>` opened with `show()` (SEM-R5); reflow at 320px and target size (RESP-R1, RESP-R5); whether a real user can finish the journey (uxauditor).
Standards: WCAG 2.2 (AA unless a card says otherwise), WAI-ARIA 1.2, ARIA in HTML, the WAI-ARIA Authoring Practices Guide (APG), HTML-AAM accessible name computation. Criteria new in 2.2 are in facts.md.
Read first: the document shell (index.html or the root layout), the global reset and base stylesheet, the primitive components (Button, Link, Input, Icon, Modal), and every custom widget in the Map's interactive inventory.

## Cards

### A11Y-R1 Control that works only with a pointer (quick)
- Leads: `scan.sh A11Y-R1` lists non-control elements (div, span, li, img, td) with a click handler on the same line. When a tag spans several lines, search the component for `onClick`, `@click`, or `on:click` and read the opening tag.
- Confirm: an element that cannot take focus by itself (div, span, li, img, td, or an `a` with no `href`) has a click handler and lacks at least one of: `tabindex="0"`, a matching role, and a key handler for the keys its role expects (Enter and Space for a button, Enter for a link, Space for a checkbox or switch). Or a custom widget (menu, tabs, listbox, combobox, slider, carousel) handles mouse events only and not its APG keys (arrows, Home, End, Escape). In React Native: a `View` or `Text` with a touch handler and no `accessible` and `accessibilityRole`.
- Not a finding if: a real `button` or `a href` inside the element does the same action and is reachable (the outer handler only widens the hit area); the element has a role, `tabIndex={0}`, and the key handling its role expects (it works; SEM-R1 may still apply); the handler only stops propagation.
- Severity: Critical when the control is on a load-bearing flow (primary action, add to cart, checkout, sign-in, main navigation) and no other keyboard path exists; High on secondary surfaces; Medium when the same action has another keyboard path on the same view.
- Fix: use the native element: `<button type="button">` for actions, `<a href>` for navigation. Only when no native element fits, add the role, `tabIndex={0}`, and the key handling of the APG pattern.
- Verify the fix: tab to the control and activate it with Enter and with Space; `scan.sh A11Y-R1` lists no click handler on a non-control without a role and key handling.
- Refs: WCAG 2.1.1, 4.1.2; APG Button pattern

### A11Y-R2 Button, link, or icon-only control with no accessible name (quick)
- Leads: `scan.sh A11Y-R2` lists buttons and links whose content is an icon, icon lines inside controls, empty `aria-label` values, iframes, and React Native touchables.
- Confirm: every name source of the control is empty: no text content (text inside an `aria-hidden` icon does not count), no `aria-label`, no `aria-labelledby` that resolves, no visually hidden text, and for an image link no `alt` text. An SVG icon with `aria-hidden` or without `<title>` names nothing. An `<iframe>` with no `title`. In React Native: a `Pressable` or `Touchable*` whose only child is an icon and that has no `accessibilityLabel`.
- Not a finding if: the icon component renders a label from a prop that the call site passes (read the icon component); a visually hidden text child exists (`sr-only`); `aria-labelledby` points to an id that exists.
- Severity: Critical when the unnamed control is a core control on a primary task (cart, checkout, submit, the close button of a blocking dialog, the main menu); High on other load-bearing surfaces; Medium for secondary controls and untitled iframes.
- Fix: name the control by its purpose: visible text, or `aria-label="Open cart"` on the button with `aria-hidden="true"` on the icon. When visible text exists, the name must contain it (WCAG 2.5.3).
- Verify the fix: every button, link, and iframe on the view has a non-empty name; an axe run reports no `button-name`, `link-name`, or `frame-title` violations.
- Refs: WCAG 4.1.2, 1.1.1, 2.4.4, 2.5.3; HTML-AAM accessible name computation

### A11Y-R3 Form field with no programmatic label (quick)
- Leads: `scan.sh A11Y-R3` lists inputs, selects, textareas, and placeholders.
- Confirm: an `input`, `select`, `textarea`, or input component has no label through `<label for>` with a matching `id`, a wrapping `<label>`, `aria-label`, or `aria-labelledby`; or its only label is a `placeholder`, a `title`, or a hover tooltip. Or a radio or checkbox group has neither `fieldset` with `legend` nor `role="group"` with a name.
- Not a finding if: the input component renders a `<label>` from a prop the call site passes (read the component); a visually hidden label exists; the field is `type="hidden"`.
- Severity: Critical when a field on a load-bearing form has no name source at all (no label, `aria-label`, `title`, or placeholder); High when the only label is a placeholder, `title`, or tooltip on a load-bearing form (browsers use a placeholder as a fallback name, so it is announced, but it vanishes while typing, is no visible label, and is usually low contrast); Medium on secondary forms and for unnamed groups.
- Fix: add a visible `<label htmlFor>` tied to the input's `id` (or wrap the input in it); keep the placeholder only as an example value.
- Verify the fix: every field of the form has a visible label tied to it; an axe run reports no `label` violations.
- Refs: WCAG 1.3.1, 3.3.2, 4.1.2

### A11Y-R4 Viewport meta blocks zoom (quick)
- Leads: `scan.sh A11Y-R4` lists `user-scalable=no`, `maximum-scale=1`, and framework viewport settings (`userScalable: false`, `maximumScale: 1`).
- Confirm: the served document's viewport meta, or the framework's `viewport` export, sets `user-scalable=no` (or `0`) or a `maximum-scale` below 2.
- Not a finding if: the meta sits in a template that no route renders (read which shell the build uses).
- Severity: Critical on any responsive surface. Safari on iOS ignores these values, but Android browsers and in-app web views honor them, so low-vision users lose pinch zoom.
- Fix: use `width=device-width, initial-scale=1` and nothing more. The usual reason for the block is iOS zooming into inputs whose font size is under 16px; fix that with a 16px input font size, never by blocking zoom.
- Verify the fix: `scan.sh A11Y-R4` returns no leads; pinch zoom works on an Android phone.
- Refs: WCAG 1.4.4, 1.4.10

### A11Y-R5 Dialog, drawer, or menu that does not manage focus (quick)
- Leads: `scan.sh A11Y-R5` lists overlay components, `role="dialog"`, `aria-modal`, and full-screen fixed layers.
- Confirm: when a custom overlay opens, focus does not move into it; or while it is modal, Tab reaches the page behind it; or on close, focus does not return to the trigger; or it lacks `role="dialog"` (or `alertdialog`), `aria-modal="true"`, and a name from `aria-labelledby`; or Escape does not close it. Also confirm the reverse: focus trapped with no key that leaves (no Escape and no reachable close control), or a blocking overlay with no keyboard or visible way to dismiss it.
- Not a finding if: a dialog library does this with default props (Radix, Headless UI, React Aria, MUI, Angular CDK; read the import and props); it is a native `<dialog>` opened with `showModal()` (the browser moves focus, makes the page inert, and closes on Escape).
- Severity: Critical when focus is trapped with no keyboard escape, a blocking overlay cannot be dismissed from the keyboard, or a focus-trap utility is present but never active on a load-bearing flow; High when a load-bearing overlay does not move, contain, or restore focus; Medium for non-modal popovers and menus.
- Fix: use `<dialog>` with `showModal()` or a proven dialog primitive. Otherwise move focus to the first control or heading on open, contain Tab, close on Escape, and return focus to the trigger.
- Verify the fix: open the overlay from the keyboard: focus lands inside, Tab cycles inside, Escape closes it, and focus returns to the trigger.
- Refs: WCAG 2.1.2, 2.4.3, 4.1.2; APG Dialog (Modal) pattern

### A11Y-R6 Focus indicator removed with no replacement (quick)
- Leads: `scan.sh A11Y-R6` lists `outline: none`, `outline: 0`, and `outline-none` in styles and class names.
- Confirm: a rule removes the outline on `:focus` or on focusable elements (a global `*:focus`, `button`, `a`, or `input` reset, or a `focus:outline-none` class), or sets `box-shadow: none` where a ring was the indicator, and no `:focus-visible` or `:focus` rule with a visible indicator (outline, ring, border, or background change) applies to the same elements with enough specificity later in the cascade.
- Not a finding if: the same element gets a `:focus-visible` style or a `focus-visible:ring-*` or `focus:ring-*` class (read the element); the removal targets elements that cannot take focus. In Tailwind v3, `outline-none` is a transparent outline that stays visible in forced-colors mode; in v4 it removes the outline (facts.md).
- Severity: Critical when the controls of a load-bearing flow show no focus indicator at all: a global reset with no replacement, or a `:focus-visible` style that a later or more specific rule defeats; High when only some load-bearing controls lose it; Medium on secondary surfaces.
- Fix: delete the global removal and style `:focus-visible` with an outline of at least 2px that has 3:1 contrast with its background; keep a transparent outline under box-shadow rings so forced-colors mode still shows focus.
- Verify the fix: tab through the load-bearing flow: every control shows a visible indicator; each `scan.sh A11Y-R6` hit has a `:focus-visible` pair.
- Refs: WCAG 2.4.7, 1.4.11, 2.4.11 (new in 2.2)

### A11Y-R7 Load-bearing audio or video with no captions or transcript (quick)
- Leads: `scan.sh A11Y-R7` lists `<video>`, `<audio>`, `<track>`, player components, and video embeds.
- Confirm: media with speech or information has no `<track kind="captions">` (or subtitles), no transcript on or linked from the page, and no text on the page that carries the same information.
- Not a finding if: the media is decorative (a muted background loop that carries no information; check its pause control under Also check); the hosted player is configured with a caption track (cite the config). A third-party embed you cannot inspect is Suspected.
- Severity: Critical when the media carries information needed for a core task (onboarding, a course, a product explanation with no text equivalent); High when a partial text alternative exists; Medium for supplementary media and for missing audio description of information shown only visually (1.2.5).
- Fix: add `<track kind="captions" srclang="en" src="intro.vtt" default>` and a transcript link next to the player.
- Verify the fix: every information-bearing player has a caption file that exists and a transcript link.
- Refs: WCAG 1.2.1, 1.2.2, 1.2.3, 1.2.5

### A11Y-R8 ARIA or in-page reference that hides or misstates the UI (quick)
- Leads: `scan.sh A11Y-R8` lists `aria-hidden`, explicit roles, ID references (`aria-labelledby`, `aria-describedby`, `aria-controls`), in-page links such as skip links, and React Native accessibility props.
- Confirm: `aria-hidden="true"` on the app root, on `main`, or on an element that contains focusable controls; a misspelled or invalid role; a widget role without its required state (`role="tab"` without `aria-selected`, `role="checkbox"` or `switch` without `aria-checked`, a combobox without `aria-expanded`); an ID reference or skip-link target (`href="#main"`) whose id does not exist; a redundant role on a native element (`role="button"` on `<button>`). In React Native: an `accessibilityRole` without the matching `accessibilityState`.
- Not a finding if: another component on the same view renders the id (search for it); the `aria-hidden` subtree is also `inert` or holds nothing focusable.
- Severity: Critical when `aria-hidden` hides the app root or the main content, or a skip link on a load-bearing surface targets a missing id (the aid is announced but absent); High when a load-bearing control misstates its role or state or hides focusable content; Medium for invalid roles and dangling references elsewhere; Low for redundant roles.
- Fix: remove wrong ARIA first (no ARIA is better than bad ARIA), then add the required state (`aria-checked={on}`), fix the id, or use the native element.
- Verify the fix: every ID reference resolves; an axe run reports no `aria-*` or `aria-hidden-focus` violations.
- Refs: WCAG 4.1.2, 1.3.1, 2.4.1; WAI-ARIA 1.2 required states and properties; ARIA in HTML

### A11Y-R9 Errors and status updates that are never announced (quick)
- Leads: `scan.sh A11Y-R9` lists `aria-live`, `role="status"` and `role="alert"`, `aria-invalid`, toasts, and React Native announcements.
- Confirm: a form error is shown but not tied to its field (no `aria-describedby` to the message and no `aria-invalid="true"`) and focus does not move to it on submit; or async results, toasts, and validation text change with no live region; or a live region exists that nothing writes to, or an `aria-live` or `role="status"` region is rendered in the same update as its first message (screen readers announce changes to a region already in the page, not a region that appears with its text; an inserted `role="alert"` is the exception and is usually announced).
- Not a finding if: focus moves to an error summary or to the first invalid field on submit; the toast library renders into a persistent live region (read its setup).
- Severity: Critical when a live region or status component on a load-bearing flow is present but never receives the message; High when errors of a load-bearing form are neither tied to their fields nor announced; Medium for other status messages.
- Fix: render one empty `role="status"` (or `aria-live="polite"`) region at mount and write messages into it; link each error with `aria-describedby` and set `aria-invalid`. In React Native, use `AccessibilityInfo.announceForAccessibility`, or `accessibilityLiveRegion` on Android.
- Verify the fix: submit the form empty: each invalid field has `aria-invalid="true"` and an `aria-describedby` that points at its message; the live region exists before the first message.
- Refs: WCAG 4.1.3, 3.3.1, 3.3.3, 1.3.1

### A11Y-R10 Image with a missing or wrong text alternative
- Leads: `scan.sh A11Y-R10` lists `<img>` and image components and generic or file-name `alt` values.
- Confirm: an `img` or image component has no `alt` attribute (a missing `alt` is not an empty one: screen readers then read the file name); an informative image (a chart, a size guide, a product photo that is the only content) has `alt=""`; `alt` is a file name or a word such as "image", "photo", or "icon"; an SVG that carries meaning lacks `role="img"` and a name.
- Not a finding if: the image is decorative, or adjacent text carries its information, and it has `alt=""` (or it is a CSS background); the image is the only content of a link or button (file that under A11Y-R2).
- Severity: High when an informative image on a load-bearing page has no usable alternative; Medium elsewhere; Low for decorative images that are announced when they should be hidden.
- Fix: write `alt` that gives the image's purpose or information (`alt="Size chart: chest 86 to 112 cm for sizes S to XL"`); use `alt=""` for decoration; give complex images a text version on the page.
- Verify the fix: every `<img>` has an `alt` attribute and informative ones have specific text; an axe run reports no `image-alt` violations.
- Refs: WCAG 1.1.1; W3C WAI Images tutorial (alt decision tree)

### A11Y-R11 Meaning carried by color alone, or text contrast known to be too low
- Leads: `scan.sh A11Y-R11` lists light text colors and utilities; read how error, required, and selected states are rendered.
- Confirm: an error, required field, selected item, or status is signaled only by color (a red border, red text with no icon or message, a green dot); or a text color and its background are both literal in the code and their contrast is below 4.5:1 (3:1 for text of at least 24px, or 19px bold, and for control borders and icons). On white, `#767676` is the lightest gray that passes 4.5:1; `#999999` is 2.8:1; Tailwind v3 `text-gray-400` (#9ca3af) is 2.5:1 and `text-gray-500` (#6b7280) is 4.8:1. Also: icons drawn only with `background-image` and indicators drawn only with `box-shadow` vanish in forced-colors mode.
- Not a finding if: the state also has text or an icon; the text belongs to a disabled control or a logo (contrast does not apply to them).
- Severity: High when a load-bearing form signals errors by color only; Medium for computed contrast failures on body text; Low for secondary text. Contrast that depends on opacity, inheritance, images, or the theme is Suspected: say a contrast check on the rendered page would confirm it.
- Fix: add a text message or icon to every color-coded state; move text colors to tokens that pass 4.5:1; add `@media (forced-colors: active)` rules or transparent outlines where box-shadow carries meaning.
- Verify the fix: every color-coded state has a text or icon cue; each text token pair passes 4.5:1 in a contrast checker.
- Refs: WCAG 1.4.1, 1.4.3, 1.4.11

## Also check
- Tab order and bypass: any `tabindex` above 0; a skip link that is not the first focusable element; a scrollable region (`overflow: auto` or `scroll`) with no focusable child and no `tabIndex={0}`; native `disabled` on a control whose purpose must stay discoverable (use `aria-disabled` and block activation).
- SPA route changes that leave focus on the old link: move focus to the new view's heading or `main`.
- Motion: animation not gated by `prefers-reduced-motion` (2.3.3 is AAA, but parallax and zoom effects trigger vestibular symptoms: Medium; Low for small fades); auto-advancing carousels, tickers, `marquee`, and auto-dismissing toasts with no pause, stop, or extend control (2.2.2 and 2.2.1, Level A: High on a load-bearing page); `<meta http-equiv="refresh">` timed redirects (2.2.1).
- Input purpose: personal-data fields without the right `autocomplete` token (1.3.5), an email or phone field as a bare `type="text"`, and numeric entry without `inputmode`.
- Paste blocked (`onPaste` with `preventDefault`) on password or one-time-code fields, or a login puzzle with no alternative: fails 3.3.8 Accessible Authentication (new in 2.2).
- A sticky header, footer, or cookie banner that can cover the focused element, with no `scroll-padding` (2.4.11, new in 2.2): Suspected unless the CSS makes it certain.
- Web Components: an interactive custom element without `delegatesFocus`, or a custom form control without `static formAssociated = true` and `ElementInternals`, so labels and forms cannot reach it.

## Paper controls (look protective, protect nothing)
- A component named `AccessibleModal` or `FocusTrap` that never moves focus or never activates.
- `role="button"` on a div with no `tabIndex` and no key handler.
- An `aria-label` that does not contain the visible text, which breaks voice control (2.5.3).
- `alt="image"`, `alt="icon"`, or a file name as alt text.
- A `:focus-visible` ring defeated by a later global `outline: none`.
- An `aria-live` region that nothing writes to, or one mounted together with its message.
- A skip link whose target id does not exist.
- A third-party `<iframe>` with no `title`.
- `aria-hidden="true"` left on the app root after a modal closes.
